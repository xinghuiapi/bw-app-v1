# 客服新模式对齐设计文档

日期：2026-05-28
项目：flutter_ui_project
对标参考：新项目客服模式（结构参考 `bw-5-27` 当前客服实现方向）

## 目标

将当前 Flutter 项目的客服页对齐到新项目客服模式。

这里的“对齐”不是近似还原，而是要求 Flutter 版本在数据来源、页面结构、空态处理、外链打开行为上与新项目客服模式保持一致；同时继续保留本项目已有的 Flutter 架构和 URL 安全校验能力。

## 范围

本次包含：
- Flutter 客服页的行为和渲染逻辑。
- 系统配置模型对 `config_kefu` 的支持。
- `config_kefu` 的解析规则和渲染逻辑。
- 客服页顶部问候卡片和空态表现。
- 保留现有安全外链校验和打开能力。

本次不包含：
- 关于我们、首页 Banner、个人中心等其他页面。
- PC 端或代理端客服逻辑。
- 后端接口改造。
- 任何旧模式兼容、旧字段回退、混合展示策略。

## 新模式参考行为

新模式客服页的核心行为如下：

1. 页面进入后调用 `/system/getlist` 获取系统配置。
2. 优先读取 `config_kefu`。
3. 如果 `config_kefu` 中存在有效项，只渲染 `config_kefu`。
4. 如果 `config_kefu` 为空或归一化后全部无效，则直接展示空态。
5. 页面顶部展示头像、`Hi，用户名` 和欢迎文案。
6. 下方展示纵向客服列表。
7. 点击客服项后执行外链打开。
8. 当没有任何客服入口时，展示空态而不是白屏。

## 当前 Flutter 实现与目标的差距

当前 Flutter 项目的 `ServiceScreen` 仍然主要依赖 `config_site.service_link` 和 `config_site.tg_link`，尚未切换为只认 `config_kefu` 的新模式，因此当前实现与目标模式不一致。

另外，当前 Flutter 客服页使用的是双列卡片布局，而新模式目标结构是纵向列表，这一点也需要对齐。

## 目标设计

### 1. 数据模型对齐

系统配置模型需要把 `config_kefu` 作为正式字段接入。

新增专用客服项模型，至少承接以下字段：
- `title`
- `link`
- `icon`

`HomeConfig` 需要对外暴露一个经过基础归一化的 `config_kefu` 列表。

旧字段 `service_link` 和 `tg_link` 可以继续保留在系统模型中，供其他非客服页场景使用，但客服页本身不再依赖它们。

除客服相关字段外，不对其他系统配置行为做额外变更。

### 2. 渲染优先级对齐

Flutter 客服页的展示数据必须严格遵循新模式规则：

1. 先构建并归一化 `config_kefu`。
2. 如果归一化后的 `config_kefu` 非空，则只渲染它。
3. 如果 `config_kefu` 为空或全部无效，则直接展示空态。

这不是“优先级 + 回退”模式，而是“单一新模式数据源”规则。

也就是说，客服页不再从旧版站点链接构建客服项；即使后端同时返回旧字段，客服页也必须完全以 `config_kefu` 为准。

### 3. 链接解析规则对齐

Flutter 端需要对齐新模式下 `config_kefu` 的链接解析容错能力。

需要支持的原始格式：
- 数组
- JSON 数组字符串
- 普通字符串
- 换行分隔字符串
- 英文逗号分隔字符串
- 中文逗号分隔字符串
- 空白字符分隔字符串

归一化规则：
- 去掉首尾空白
- 去掉反引号
- 去掉外层引号
- 去掉异常空白
- 过滤空值

对于 `config_kefu`，只有 `link` 归一化后非空的项才允许进入渲染。

### 4. 页面结构对齐

Flutter 客服页需要对齐新模式当前信息结构：

1. 顶部导航栏显示客服标题。
2. 顶部展示白色问候卡片。
3. 问候卡片中展示头像、`Hi，用户名` 和欢迎语。
4. 主体区域使用纵向列表展示客服项，不再使用双列网格。
5. 客服项有图标时展示图标。
6. 客服项展示主标题和操作文案。
7. 当加载结束且没有任何客服项时，展示空态文案。

实现上仍然保持 Flutter 的组件写法，但页面可见结构要以新模式为准。

### 5. 标题命名规则

当渲染 `config_kefu` 时：
- 如果后端返回了 `title`，优先使用后端标题。
- 如果没有返回 `title`，则按 bw m1 规则生成。
- 单个客服项时，使用默认在线客服标题。
- 多个客服项时，使用带序号的在线客服标题。

Flutter 现有多语言文案需要检查是否足够支撑新模式下的命名规则；仅在缺失时补齐，不做无关扩展。

### 6. 外链打开行为

Flutter 端继续保留现有 `UrlPolicy` 安全校验和外链打开能力。

行为要求：
- 打开前先归一化 URL。
- 对非法或被策略拦截的链接，沿用现有错误提示行为。
- 对合法链接执行外部打开。
- 如果打开失败，沿用现有失败反馈。

这里不要求机械照搬网页端的 `window.open` 实现，而是要求在行为结果上对齐新模式，同时保留本项目已有的安全边界。

### 7. 异常与空态处理

客服页在面对不完整或脏数据时仍需稳定工作。

规则如下：
- 如果 `config_kefu` 存在，但归一化后全部无效，则视为“空”，直接展示空态。
- 如果所有来源都为空，则展示客服空态。
- 如果页面处于加载中，则保持现有加载态表现。
- 单个非法链接要在渲染前被过滤掉，不能直接展示到页面上。

### 8. 验证策略

验证需要覆盖以下场景：
- 只返回 `config_kefu`
- 同时返回 `config_kefu` 和旧版链接，确认旧版链接被忽略
- `config_kefu` 存在脏数据或非法项
- 完全空配置
- 链接格式为数组、JSON 字符串、逗号、中文逗号、换行和空白分隔
- 合法链接与非法链接的安全打开行为

## 预期改动位置

大概率会涉及以下 Flutter 文件：
- `lib/models/home/home_models.dart`
- `lib/screens/main/main_screens.dart`
- 如有需要，补充系统配置归一化辅助逻辑
- 如有缺失，再补客服相关翻译文案

## 风险

1. 引入严格优先级后，当后端同时下发 `config_kefu` 和旧版站点链接时，页面可见结果会发生变化。
2. 当前仓库里已有“客服页已对齐”的历史文档，但那一版只覆盖了旧版 `service_link/tg_link` 逻辑，不代表已经切换到新模式。
3. 如果后端未及时提供 `config_kefu`，客服页将直接空态，这属于符合新模式但需要业务确认的结果。
4. 当前页面是网格布局，目标页面是列表布局，存在 UI 回归风险，需要实际跑页面确认。

## 验收标准

1. Flutter 客服页只使用 `config_kefu` 构建客服列表。
2. 当 `config_kefu` 中存在有效项时，页面正确展示客服列表。
3. 当 `config_kefu` 为空或全部无效时，页面直接展示空态，不再回退旧字段。
4. 页面结构与新模式保持一致：导航栏、问候卡片、纵向客服列表、空态。
5. 点击客服项后，通过本项目安全外链能力打开合法链接。
6. 不影响其他无关页面行为。
7. 兼容现有 Flutter Provider 架构。

## 非目标

本次不会去实现以下内容：
- 旧模式 `service_link/tg_link` 的客服页回退
- `business_link`
- 多类型客服副标题
- 混合来源同时展示
